# Benchmark 任务工作区

本目录存放 **Benchmark Tasks 对应的实际编程项目环境**（Python 源码、测试、配置与其他必要资源），是 Coding Agent 实验的真实操作对象。

## 1. 目录职责

`benchmark/workspaces/` 下每个子目录对应 `benchmark/tasks.json` 中的一条任务，提供该任务从初始代码状态开始执行所需的全部文件。任务清单与评价标注仍分别保存在 `benchmark/tasks.json` 和 `benchmark/expected_tools.json`。

## 2. 命名规则

- 每个任务使用一个独立目录，**目录名必须与 `tasks.json` 中的 `task_id` 完全一致**。
- 当前 `tasks.json` 使用 `task_001` / `task_002` / `task_003` 作为占位 ID，因此本目录下的占位目录同名。
- 若后续把任务 ID 调整为 `T01`、`T02` 这类形式，对应目录需同步重命名，始终保持“任务 ID = 目录名”。
- `tasks.json` 中的 `project_path` 字段应在真实任务落地时指向 `benchmark/workspaces/<task_id>`（由成员 B 统一对齐；当前占位值不改动）。

## 3. 内部结构

任务目录内部不要求统一结构，可按任务需求自行组织，例如：

```
task_001/
├── README.md          # 任务背景与运行方式（建议提供）
├── src/               # 业务代码
├── tests/             # 测试用例
└── pyproject.toml     # 项目配置（或 requirements.txt，视任务而定）
```

> 当前各任务目录仅有一个 `.gitkeep` 占位文件，真实的 `src/`、`tests/` 等由成员 B 后续创建。

## 4. 初始状态一致

- 每个任务的所有实验（三组模式、多次重复）都必须**从相同的初始代码状态开始**。
- 初始状态以本目录中该任务目录的内容为准；任务初始状态确定后，不应在实验过程中被直接修改。

## 5. 隔离与重置

- 不同实验组之间、同一任务的重复实验之间，必须使用**独立的工作副本**，或通过**可靠的重置机制**恢复初始状态。
- 推荐做法：实验开始前把 `benchmark/workspaces/<task_id>/` 复制到独立的临时实验目录，Agent 只在副本上读写；实验结束后丢弃副本。
- 备选做法：将任务工作区纳入版本管理，实验前用 `git checkout` / `git clean` 重置。无论采用哪种方式，都必须保证后一组实验不受前一组代码修改的影响。

## 6. 分工

| 成员 | 职责 |
|---|---|
| 成员 B | 创建并维护具体任务工作区（初始代码、测试、配置），保证每个任务可从干净状态复现 |
| 成员 C | 实验运行时使用这些工作区：负责复制 / 重置，并驱动 Agent 在副本上执行任务 |

成员 A、成员 D 不直接改动本目录内容；本目录的约定变更需同步更新 `README.md` 与 `docs/architecture.md`。
